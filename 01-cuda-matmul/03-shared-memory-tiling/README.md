# 实验 03：Shared Memory Tiling

## 先看一个重复使用的例子

和实验 01 一样，一个线程计算一个 `C[row,col]`。假设一个 block 负责 `C` 的 `16×16` 区域。只看 `k=0`：

- 同一行的 16 个输出都要用同一个 `A[row,0]`。
- 同一列的 16 个输出都要用同一个 `B[0,col]`。

实验 02 已经看到：naive kernel 对 A 有同地址广播，对 B 有连续读取。因此“重复使用”**不表示一定发生了同样多次显存访问**；GPU 的广播和缓存会帮忙。但程序仍在每个输出线程的循环中发起读取，没明确让整个 block 保存一块数据供后续计算使用。

## 把大矩阵切成小块

本实验仍用 `block(16,16)`，每个 block 计算 C 的一个 `16×16` 小块。`K` 方向也每次前进 16：

```text
C 的 16×16 小块 += A 的 16×16 小块 × B 的 16×16 小块
```

比如计算 `C[0:16,0:16]`，第一轮需要 `A[0:16,0:16]` 和 `B[0:16,0:16]`；第二轮需要 `A[0:16,16:32]` 和 `B[16:32,0:16]`。每轮的步骤是：

1. 256 个线程各自从 A、B 加载一个元素，共同填满 `a_tile` 和 `b_tile`。
2. `__syncthreads()`：等这个 block 的所有线程完成加载。
3. 每个线程从 shared memory 取自己需要的 16 对数，累加到自己的 `sum`。
4. 再次 `__syncthreads()`：所有线程算完后，才允许下一轮覆盖这两块数据。

`__shared__` 数组属于**一个 block**，同一个 block 内的线程可以共同读写。不同 block 不能直接共享这些数组。最后一块可能不足 16 个元素；代码会把越界位置填成 `0`。所有线程都必须参加两次同步，所以边缘线程也不能在同步前直接 `return`。

对一个完整的 `K` 小块，naive 版本的 256 个线程各要读取 16 个 A 和 16 个 B，代码层面是 `256×(16+16)=8192` 次加载；tiled 版本从全局内存装入 `256+256=512` 个元素，然后从 shared memory 反复读取。**这是代码中的加载次数，不是实际显存事务数，也不意味着速度必然提高 16 倍。**同步、计算、缓存和矩阵形状都会影响结果。

## 运行与验证

在项目根目录的 Windows PowerShell 中运行：

```powershell
.\scripts\build-windows.ps1 -Lesson Tiled
```

Linux / WSL 可在当前目录运行：

```bash
nvcc -O2 -std=c++17 -arch=sm_120 sgemm_tiled.cu -o sgemm_tiled
./sgemm_tiled
```

程序用固定种子的随机 FP32 输入：

| `M×N×K` | 用途 |
| --- | --- |
| `37×53×29`、`129×257×65` | 非整齐尺寸；全部输出与 CPU 双精度参考值比较 |
| `1×1024×1024` | 小 batch、单行输出，接近推理中的矩阵乘向量形状 |
| `64×1024×1024` | 中等 batch |
| `1024×1024×1024` | 大方阵 |

大形状会逐元素对照 naive GPU 输出，并抽查首、中、末位置的 CPU 参考值。计时使用 CUDA event，在预热后连续运行 50 次，输出平均 kernel 时间；不包含输入生成、内存分配与拷贝。`GFLOP/s = 2MNK / 时间`。两个版本都是普通 FP32 SGEMM，可以直接对照。

## 这节的练习

先只看 `sgemm_tiled` 的第一轮：当 `blockIdx=(0,0)`、`threadIdx=(2,3)`、`start=0` 时，这个线程从 A 和 B 各加载哪个矩阵元素到 shared memory？它最终负责写哪个 `C[row,col]`？

然后运行程序，记下三个计时形状的 naive 和 tiled 时间。观察哪个形状受益、哪个没有受益。尤其留意 `M=1` 时，一个 `16×16` block 中只有一行线程负责有效输出；shared memory 分块会有额外成本。

完成标准：能指出两次同步分别保护什么，能解释边缘块为什么填零，以及能根据三个形状的实测结果说出这种简单分块的适用范围。
