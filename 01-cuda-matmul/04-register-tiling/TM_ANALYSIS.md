# 为什么自动编译时 `TM=8` 最快？

本记录分析实验 04 的普通 FP32 `sgemm_register`，输入为 `M=N=K=1024`，block 为 `16×16=256` 个线程。硬件是 RTX 5060 Ti（36 个 SM），CUDA `nvcc 13.3.73`，编译参数与项目构建脚本一致。`TM` 是**每个线程计算的 C 行数**。以下数据只对当前 kernel、矩阵形状和设备有效。

## 1. 先确认现象

使用 CUDA event，每个版本预热后连续启动 50 次；按 `TM=4→8→16→32` 的顺序交错运行三轮。全部正确性检查为 `PASS`。

| `TM` | 三轮时间 (ms) | 中位时间 (ms) | 中位有效算力 (GFLOP/s) |
| ---: | --- | ---: | ---: |
| 4 | 0.478 / 0.478 / 0.478 | 0.478 | 4493.1 |
| **8** | **0.401 / 0.401 / 0.401** | **0.401** | **5348.9** |
| 16 | 0.541 / 0.541 / 0.541 | 0.541 | 3968.6 |
| 32 | 0.916 / 0.916 / 0.916 | 0.916 | 2345.4 |

## 2. `TM` 增大带来的收益越来越小

固定一轮的 16 个 `k`，一个 block 计算 `16×TM` 行、16 列的 C：共 `256×TM` 个输出。源码装入 shared memory 的 A 元素有 `256×TM` 个，B 元素只有 `256` 个。因此，对**每个输出元素**，这一轮从全局内存发出的元素加载数是：

```text
(256×TM + 256) / (256×TM) = 1 + 1/TM
```

| `TM` | 每个输出对应的源码级全局加载元素数 |
| ---: | ---: |
| 4 | 1.2500 |
| 8 | 1.1250 |
| 16 | 1.0625 |
| 32 | 1.03125 |

`TM=4→8` 在这个模型里减少了 10% 的加载；`8→16` 只减少约 5.6%；`16→32` 只减少约 2.9%。这些是**源码层面的元素加载数**，不是实际 DRAM 事务数；缓存可能使真实显存差异更小。每个输出需要的乘加次数没有变化。

## 3. 实测资源与可驻留 block 数

用 `nvcc --resource-usage` 读取编译结果，并调用 `cudaFuncGetAttributes` 与 `cudaOccupancyMaxActiveBlocksPerMultiprocessor` 查询静态资源和理论驻留上限。设备报告每个 SM 有 65536 个寄存器、102400 字节 shared memory、最多 1536 个线程。

| `TM` | 寄存器/线程 | shared memory/block | 寄存器溢出 | 理论驻留 block/SM | 理论驻留线程/SM | 整个 grid 的 block 数 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 4 | 40 | 5120 B | 0 | 6 | 1536 | 1024 |
| **8** | **55** | **9216 B** | **0** | **4** | **1024** | **512** |
| 16 | 56 | 17408 B | 0 | 4 | 1024 | 256 |
| 32 | 80 | 33792 B | 0 | 2 | 512 | 128 |

这里的“理论驻留”是资源允许的上限，**不是运行时实际活跃线程数**。`TM=8` 与 `TM=16` 的上限相同，且都没有溢出，所以不能把 `TM=16` 的变慢解释成寄存器溢出或理论驻留 block 数下降。`TM=32` 的上限降到每 SM 2 个 block，这是它明显变慢的一个有力线索，但还不是完整的运行时证明。

## 4. 检查 `TM=16` 是否只因 grid 太小

`M=1024` 时，`TM=8` 有 512 个 block，`TM=16` 只有 256 个。设备有 36 个 SM，两者理论上都能每 SM 驻留 4 个 block，所以一次最多分别可容纳相同的 `36×4=144` 个 block。按这个上限粗略分批，`TM=8` 的 grid 约需 3.6 批，`TM=16` 约需 1.8 批；这是静态估算，不是实测调度过程。

把 M 增大，能增加两者的 block 数。如果速度差只来自原来 grid 的尾部不足，差距应明显缩小。下面是两种配置交错运行三轮的**中位时间**，全部为 `PASS`：

| 形状 `M×N×K` | `TM=8` | `TM=16` | `TM=16` 相对耗时 |
| --- | ---: | ---: | ---: |
| `1024×1024×1024` | 0.401 ms | 0.541 ms | 约 1.35 倍 |
| `2048×1024×1024` | 0.775 ms | 1.002 ms | 约 1.29 倍 |
| `4096×1024×1024` | 1.534 ms | 1.949 ms | 约 1.27 倍 |

扩大 M 后差距缩小，但仍存在。因此 `M=1024` 时 block 数较少**可能贡献了部分差距**，并不是唯一原因。`TM=16` 每个 block 执行更长的计算、使用更大的 shared memory 小块，编译器也可能生成不同的指令；下面用运行时指标继续检查。

## 5. Nsight Compute：`TM=16` 多执行了哪些指令？

现在本机已有 Nsight Compute 2026.4。在相同的 `1024³` 形状上，分别编译 `TM=8/16`，每个程序只运行 register kernel：预热 3 次后采集第 4 次启动。每份报告采集 17 个 pass。下面的指令计数是 **warp 级执行次数**，不是每个线程的加载元素数；Nsight Compute 的 replay 时长也不能替代上面的 CUDA event 基准时间。

| 指标 | `TM=8` | `TM=16` | 观察 |
| --- | ---: | ---: | --- |
| CUDA event 基准时间 | 0.401 ms | 0.541 ms | `TM=16` 多约 35% |
| Nsight Compute 采集时长 | 442.59 μs | 593.60 μs | 比例与基准接近 |
| 理论 occupancy | 66.67% | 66.67% | 资源上限相同 |
| 实际 occupancy | 61.66% | 55.16% | `TM=16` 少 6.50 个百分点 |
| shared memory 加载指令 | 12,582,912 | 18,874,368 | **`TM=16` 多 50%** |
| LSU 管线指令总数 | 17,342,464 | 23,367,680 | `TM=16` 多约 35% |
| FMA 管线指令总数 | 37,584,896 | 37,171,200 | 计算指令量接近 |
| MIO 队列等待，报告中的每 warp 平均值 | 4.83 | 8.90 | `TM=16` 等待明显增加 |
| 每调度器每周期可发射的 warp | 1.41 | 1.05 | 更少 warp 准备好执行 |
| DRAM 吞吐占峰值 | 4.36% | 3.40% | 没有打满显存带宽 |

**为什么 shared memory 加载指令会变多？** `cuobjdump` 看到的内层循环 SASS（GPU 实际执行的机器指令）不同：

| 一个内层循环体 | `TM=8` | `TM=16` |
| --- | ---: | ---: |
| 处理的 `k` 值 | 4 个 | 2 个 |
| 加载 A 的指令 | 8 条 `LDS.128` | 16 条 `LDS.64` |
| 加载 B 的标量 `LDS` | 4 条 | 2 条 |
| `FFMA` 乘加 | 32 条 | 32 条 |

`LDS.128` 一条指令让每个线程取 4 个 FP32 数，`LDS.64` 取 2 个。两版每个循环体都做 32 条乘加，但 `TM=16` 要发出 **18 条** shared memory 加载指令，`TM=8` 只要 **12 条**。整个 grid 的 warp 级内层循环次数恰好相同：`TM=8` 是 `512 block × 8 warp × 256 次 = 1,048,576`；`TM=16` 是 `256 block × 8 warp × 512 次 = 1,048,576`。乘上每轮的 12 或 18 条加载指令，正好得到 Nsight Compute 的 `12,582,912` 和 `18,874,368`。

这与运行时现象一致：`TM=16` 的 MIO 队列等待从 4.83 增到 8.90，调度器能找到可执行 warp 的频率下降，实际 occupancy 也降低。两版 shared load 的 bank conflict 分别为 `14,990` 和 `13,572`，`TM=16` 没有增加；shared load wavefront 反而由约 `20.99` 百万降至 `18.89` 百万。因此这里的突出变化是**加载指令的发射与排队压力**，不能简单说成读取了更多 shared memory 数据或发生了更多 bank conflict。

原始报告保存在本机 `.local/tm-profile/ncu-tm8.ncu-repz`、`ncu-tm16.ncu-repz` 和 `ncu-memory-tm8.ncu-repz`、`ncu-memory-tm16.ncu-repz`；该目录不纳入 Git。

## 6. 受控实验：改变 K 循环展开数

为了验证上面的指令差异是否真的影响速度，在 register kernel 的内层 K 循环前加入可选的 `#pragma unroll REGISTER_K_UNROLL`；**同一 TM 的两个版本**只改变展开策略，block 映射和输入形状不变。`auto` 是原来的代码，`u2/u4` 分别强制一个循环体处理 2/4 个 K 值。四个版本都用相同种子的随机数据，预热 10 次；每个形状计时 5 轮、每轮 60 次 kernel 启动，按正序和倒序各运行一遍，取 10 个结果的中位数。每个版本和形状都抽查 CPU 结果通过。

课程构建脚本现在提供相同的编译开关，例如 `-Lesson Register -ThreadTileM 16 -KUnroll 4`。省略 `-KUnroll` 就是自动版本。该脚本会运行课程中的多个形状；下表的中位数来自本机 `.local/tm-deep/` 的独立计时程序，四个版本均在同一程序里采样，不能直接用课程程序的一次输出替代。

| 版本 | A 的 SASS 加载 | 寄存器/线程 | 理论 block/SM | 实际 occupancy | MIO 等待 | `1024³` 中位时间 | `4096×1024×1024` 中位时间 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `TM=8 auto` | `LDS.128` | 55 | 4 | 61.66% | 4.83 | 0.408 ms | 1.544 ms |
| `TM=8 u2` | `LDS.64` | 40 | 6 | 84.91% | 12.50 | 0.557 ms | 2.128 ms |
| `TM=16 auto` | `LDS.64` | 56 | 4 | 55.16% | 8.90 | 0.541 ms | 1.954 ms |
| `TM=16 u4` | `LDS.128` | 95 | 2 | 31.54% | 1.88 | **0.400 ms** | **1.486 ms** |

这里有两个关键对照：

1. **固定 `TM=16`，grid 完全不变**，强制展开 4 个 K 后，shared load 指令从 `18.87` 百万降到 `10.49` 百万，MIO 等待从 `8.90` 降到 `1.88`，`1024³` 时间从 `0.541` 降到 `0.400 ms`。原来 `TM=8 auto` 与 `TM=16 auto` 相差 `0.133 ms`；这一次编译策略改变带来的净改善为 `0.141 ms`，足以覆盖那段差距。
2. **固定 `TM=8`**，强制只展开 2 个 K 后，shared load 指令从 `12.58` 百万升到 `20.97` 百万，实际 occupancy 虽然从 `61.66%` 升到 `84.91%`，时间仍从 `0.408` 升到 `0.557 ms`。因此在这个 kernel 上，更高 occupancy 没有抵消取数指令和 MIO 等待增加的代价。

这两组实验同时改变了循环展开和 SASS 加载宽度，不能把 `0.141 ms` 全部归给 `LDS.128` 一项；它是**编译策略改变的净效应**。但同一 `TM` 内 grid 不变，已经排除了“block 数变化是全部原因”。

### 编译器为什么没有自动选择 `u4`？

强制 `TM=16 u4` 时，寄存器从 `56` 增到 `95` 个/线程，理论驻留从每 SM 4 个 block 降到 2 个。把这个版本的寄存器上限设为 80 或 64，编译器会产生本地内存溢出；`1024³` 时间分别回升到 `0.444` 和 `0.479 ms`。这说明宽加载和更大的循环展开确实有寄存器代价，限制寄存器也会引入额外代价。

从生成结果看，自动版本选择较小展开数，维持了每 SM 4 个 block 的理论驻留；**编译器可能是在权衡寄存器与 occupancy**。这是根据输出作出的推断，工具没有给出内部启发式的理由。对当前 GPU 和形状，强制 `u4` 虽然只剩约 `31.5%` 实际 occupancy，仍比自动版快约 `26%`，说明自动权衡没有找到最快点。生成的 PTX 都使用标量 `ld.shared.b32`；最终的 `LDS.64/128` 组合出现在 SASS 阶段。

受控实验的构建脚本、逐轮计时 CSV、SASS 和 Nsight Compute 报告保存在本机 `.local/tm-deep/`。这些文件不纳入 Git；表格保留了可复查的关键结果。

术语与工具说明见 NVIDIA 的 [`#pragma unroll` 文档](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/cpp-language-extensions.html)、[`--maxrregcount` 文档](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/)和 [Nsight Compute 的 MIO stall 解释](https://docs.nvidia.com/nsight-compute/ProfilingGuide/)；上面的具体数值来自本机报告。

## 结论与未验证部分

对这个 kernel，`TM=8` 是已测试的四个值中的折中点：比 `TM=4` 有更多 B 复用；继续增大到 `16/32` 时，额外复用收益变小，而每个 block 的资源和工作量继续增长。`TM=32` 还降低了理论驻留上限。

对 `TM=16`，现在有更具体的证据：**自动编译的内层循环展开较少，生成较窄的 shared memory 加载，导致更多 LDS/LSU 指令和更重的 MIO 等待。**固定 `TM=16` 和 grid 只改展开策略，就能从 `0.541` 降至 `0.400 ms`；这比原先 `TM=8/16` 的差距还大。因此 block 数减少可以贡献部分耗时，但不是解释速度差所必需的主因。仍不能把循环展开、加载宽度、寄存器数、occupancy 的影响精确拆成独立百分比，因为它们会同时变化；编译器内部为何默认选较小展开数也没有直接证据。

## 从这次实验带走什么

1. **源码级复用只是起点，要检查实际指令。** `TM=16` 让每个 B 值服务更多输出，但自动编译时内层循环的 shared memory 加载指令反而比 `TM=8` 多 50%。因此优化时既要算数据复用，也要看 SASS 指令数、等待和实际耗时。
2. **Occupancy 是帮助隐藏等待的手段，不是越高越好的成绩。** `TM=16 u4` 的实际 occupancy 只有 `31.54%`，却比 `TM=16 auto` 更快；`TM=8 u2` 升到 `84.91%`，反而更慢。寄存器、指令发射和并行度需要一起权衡。
3. **编译器默认选择值得测量。** 强制展开 K 循环足以消除原来 `TM=16` 相对 `TM=8` 的明显劣势，但会多用寄存器。编译器为何默认采用较小展开数仍是推断，不能把它说成已证实的内部决策。
4. **用受控对照定位原因。** 先测正确性和时间，再看 profiler 与 SASS，固定 `TM`、grid 和输入形状，只改变展开策略后重测。`0.541→0.400 ms` 是这一组联动变化的净效果，不能精确分摊给加载宽度、寄存器或 occupancy。`TM=16 u4` 的 `0.400 ms` 与 `TM=8 auto` 的 `0.408 ms` 很接近，也不足以宣称前者稳定胜出。

编译资源的含义见 [NVIDIA NVCC 文档](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/)；理论驻留上限由 [CUDA Occupancy API](https://docs.nvidia.com/cuda/cuda-runtime-api/cuda_runtime_api/group__CUDART__OCCUPANCY.html) 计算。NVIDIA 的 [Compute Triage Guide](https://docs.nvidia.com/nsight-compute/ComputeTriage/) 说明了如何用运行时指标区分寄存器、shared memory、并行度及其他限制。静态资源和理论 occupancy 只能缩小原因范围，不能替代运行时分析。
