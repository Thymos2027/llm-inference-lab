# FP32 矩阵乘法：从 naive 开始的性能记录

本页按学习顺序记录 `C[M,N] = A[M,K] × B[K,N]` 的实测表现。形状写作 `M×N×K`。这里的“有效算力”按 `2MNK ÷ kernel 秒数 ÷ 10^9` 计算，单位为 `GFLOP/s`；数值越大，表示同样的矩阵乘法完成得越快。它不是 GPU 的标称峰值或显存带宽。

## 当前走到了哪一步

| 阶段 | 方法 | 对 `1024³` 的观察 |
| --- | --- | --- |
| 01 | **最初的 naive**：一个线程算一个 C 元素 | `1.410 ms`，`1522.8 GFLOP/s`；课程起点 |
| 02 | 线程映射对照：`columns 32×8` | 与 naive 接近，三次运行不能证明稳定提速 |
| 03 | **Shared Memory Tiling**：block 合作加载并复用 A/B | 与同程序 naive 配对比较：`1.392 → 1.052 ms`，约 `1.32×` |

实验 02 的 `rows` 是故意采用跨行访问的反例，不是优化路线。实验 03 从原来的 `16×16` 映射直接加入 shared memory 分块，并未叠加实验 02 的 `32×8` 映射。因而不能把不同实验的加速比相乘，当作一个已实现的累计加速比。

## 测量条件

- 日期：2026-11-10，Windows；GPU：NVIDIA GeForce RTX 5060 Ti，16 GB，compute capability 12.0；驱动 `610.88`。
- 编译器：CUDA `nvcc 13.3.73`，参数 `-O2 -std=c++17 -arch=sm_120 -Xcompiler /utf-8`。
- 输入：固定种子的随机 FP32 数据；三个程序采用相同的矩阵形状。输出均为 FP32。计时只包含 GPU kernel，不包含数据生成、内存分配、CPU/GPU 拷贝和 CPU 校验。
- 方法：每种 kernel 预热 3 次，CUDA event 计时连续 50 次启动，取平均；每个程序再独立运行 3 次，下表列出这 3 次的平均值及中位数。**加速比 = 同形状、同程序的 naive 中位时间 ÷ 当前版本中位时间**。
- 正确性：本次记录全部为 `PASS`。实验 01 的默认 `37×53×29`、实验 02 的 `37×53×29`、实验 03 的 `37×53×29` 和 `129×257×65` 均用 CPU 参考值检查；计时形状则抽查 CPU 参考值。实验 02、03 还逐元素与各自的 naive GPU 结果比较。

### 大方阵：`1024×1024×1024`

| 阶段 / kernel | 三次时间 (ms) | 中位时间 (ms) | 中位有效算力 (GFLOP/s) | 同程序加速比 |
| --- | --- | ---: | ---: | ---: |
| 01 最初 naive `16×16` | 1.410 / 1.449 / 1.393 | 1.410 | 1522.8 | 1.00× |
| 02 original `16×16` | 1.516 / 1.479 / 1.521 | 1.516 | 1416.1 | 1.00× |
| 02 columns `32×8` | 1.505 / 1.456 / 1.453 | 1.456 | 1474.9 | 1.04× |
| 02 rows `32×8`（反例） | 11.911 / 11.922 / 11.894 | 11.911 | 180.3 | 0.13× |
| 03 naive `16×16` | 1.392 / 1.392 / 1.392 | 1.392 | 1542.6 | 1.00× |
| 03 tiled `16×16` | 1.060 / 1.035 / 1.052 | 1.052 | 2042.3 | 1.32× |

**01 naive、02 original、03 naive 是相同的计算方式。** 三个程序的测量值仍有差异，说明跨程序直接比较几百分点的变化不可靠。`columns` 在本轮实验 02 内约快 4%，但此前本机也出现过 `original` 更快的结果；现在只能说二者接近。`tiled` 的配对差距较大，在这个大方阵上确实有收益。

### 单行输出：`1×1024×1024`

| 阶段 / kernel | 三次时间 (ms) | 中位时间 (ms) | 中位有效算力 (GFLOP/s) | 同程序加速比 |
| --- | --- | ---: | ---: | ---: |
| 01 最初 naive | 0.023 / 0.023 / 0.023 | 0.023 | 90.0 | 1.00× |
| 02 original | 0.023 / 0.023 / 0.023 | 0.023 | 90.0 | 1.00× |
| 02 columns | 0.023 / 0.023 / 0.023 | 0.023 | 90.0 | ≈1.00× |
| 02 rows（反例） | 0.058 / 0.096 / 0.058 | 0.058 | 36.4 | ≈0.40× |
| 03 naive | 0.023 / 0.024 / 0.023 | 0.023 | 90.0 | 1.00× |
| 03 tiled | 0.025 / 0.026 / 0.025 | 0.025 | 82.7 | 0.92× |

这里的计算量小，时间只显示到 `0.001 ms`，非常接近的数字不适合细排高低。简单的 `16×16` tiled kernel 在 `M=1` 时只有一行线程写有效输出，加载和同步的成本难以摊薄。

### 中等 batch：`64×1024×1024`

| 阶段 / kernel | 三次时间 (ms) | 中位时间 (ms) | 中位有效算力 (GFLOP/s) | 同程序加速比 |
| --- | --- | ---: | ---: | ---: |
| 01 最初 naive | 0.107 / 0.107 / 0.107 | 0.107 | 1255.6 | 1.00× |
| 02 original | 0.107 / 0.107 / 0.107 | 0.107 | 1255.2 | 1.00× |
| 02 columns | 0.105 / 0.105 / 0.135 | 0.105 | 1280.9 | ≈1.02× |
| 02 rows（反例） | 0.799 / 0.866 / 0.820 | 0.820 | 163.7 | 0.13× |
| 03 naive | 0.107 / 0.107 / 0.107 | 0.107 | 1256.6 | 1.00× |
| 03 tiled | 0.084 / 0.080 / 0.080 | 0.080 | 1675.3 | 1.34× |

`M=64` 时分块开始有明显收益。这个形状和 `M=1` 放在一起看，能避免只凭大方阵结果判断方法是否适合推理中的小 batch。

## 如何复现并继续推进

在仓库根目录运行：

```powershell
.\scripts\build-windows.ps1 -Lesson Naive -Benchmark
.\scripts\build-windows.ps1 -Lesson Coalesced
.\scripts\build-windows.ps1 -Lesson Tiled
```

各阶段的代码与练习见[实验 01](01-naive/README.md)、[实验 02](02-coalesced-access/README.md)、[实验 03](03-shared-memory-tiling/README.md)。下一步可研究寄存器分块，让每个线程累加多个 C 元素，再用相同形状和配对基线测试。针对 `M=1`，还应单独考虑适合矩阵乘向量的线程分工。

“榨干硬件性能”需要结合性能分析工具查看实际访存、计算单元利用率和时钟；仅凭 GFLOP/s 不能算出硬件利用率。以后每加一个方法，都记录精度、形状、三次时间、正确性和同程序基线。FP16/BF16 Tensor Core 实验应单独成表并标明输入、累加和输出精度；它与本页的普通 FP32 SGEMM 不能直接当作同一种计算比较加速比。
