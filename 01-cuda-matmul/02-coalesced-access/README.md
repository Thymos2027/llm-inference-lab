# 实验 02：合并访存与线程映射

## 这次要理解什么

先看实验 01 的 `sgemm_naive`。矩阵按行连续存储，`block(16,16)` 中的 `threadIdx.x` 变化最快。一个 warp 的 32 个线程因此覆盖 **两行、每行 16 列**。在固定 `k` 时：

| 访问 | 相邻列的线程看到什么 | 结果 |
| --- | --- | --- |
| `A[row*K+k]` | 同一行的 16 个线程读同一地址 | 可广播，但每个输出元素仍会重复遍历 A |
| `B[k*N+col]` | 读相邻的 16 个 `float` | 已经是合并访存的访问模式 |
| `C[row*N+col]` | 写相邻的 16 个 `float` | 已经是合并访存的访问模式 |

**重点：原始 kernel 并非完全没有合并访存。** 它慢的一个主要原因是没有把读取的 A/B 数据在 block 内显式复用。Shared Memory Tiling 将在下一节解决这件事。本节只改变线程与输出元素的对应方式，观察访存模式。

CUDA warp 有 32 个 lane。对于按行存储的矩阵，让相邻 lane 访问相邻列，通常能把相邻线程的内存请求合并到较少的内存事务中；具体事务数还取决于对齐、缓存和硬件实现。

`sgemm_access.cu` 有三个版本：

| 版本 | block | 一个 warp 负责 | 固定 `k` 时的主要访存 |
| --- | --- | --- | --- |
| `original` | `16×16` | 两行、每行 16 列 | B 连续，A 同行广播，C 连续 |
| `columns` | `32×8` | 一行的 32 个相邻列 | B 连续，A 同行广播，C 连续 |
| `rows` | `32×8` | 同一列的 32 个相邻行 | A 跨 `K` 个元素，B 同列广播，C 跨 `N` 个元素 |

`columns` 和 `rows` 使用相同的线程数、输入与乘加顺序。`rows` 只改变线程到输出的映射，用来对照访存。它仍然是正确的矩阵乘法。

## 运行

Windows PowerShell，在项目根目录执行：

```powershell
.\scripts\build-windows.ps1 -Lesson Coalesced
```

Linux / WSL，在 `01-cuda-matmul/02-coalesced-access` 目录执行：

```bash
nvcc -O2 -std=c++17 -arch=sm_120 sgemm_access.cu -o sgemm_access
./sgemm_access
```

程序先用 `37×53×29` 的非整齐尺寸和 CPU 双精度参考值检查三个版本；再对 `1×1024×1024`、`64×1024×1024`、`1024×1024×1024` 逐元素比较三个 GPU 输出、抽查 CPU 参考值，并用 CUDA event 测 50 次 kernel 启动的平均时间。计时不包含输入生成、内存分配和主机与设备之间的拷贝。`GFLOP/s = 2MNK / 时间`，其中一次乘法和一次加法各计一次浮点运算。各形状的实测数据见[性能记录](../BENCHMARKS.md)。

性能结果受 GPU 时钟、温度、其他进程和缓存状态影响。可以运行几次看趋势，不必追求某个固定数值。`columns` 不保证一定比 `original` 快；二者都具备连续访问，而 block 形状还会影响调度等因素。
